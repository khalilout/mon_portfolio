Plateforme Articles & Amis — API Laravel + Front React

Réseau social minimaliste : articles, commentaires, amis, profils

Full‑stack

Ce projet met en avant ma capacité à livrer une application de bout en bout : une API REST sécurisée d'un côté, une interface React moderne de l'autre. L'intérêt principal est de démontrer la maîtrise du cycle complet — modélisation des données, authentification, logique métier (relations sociales), consommation d'API et gestion d'état côté client — sur un cas réaliste plutôt qu'un simple CRUD.

Pipeline météo serverless — AWS Lambda, S3 & DynamoDB

ETL événementiel en Afrique de l'Ouest, 100% serverless

Cloud / ETL

Ce projet illustre une chaîne ETL serverless complète sur AWS, sans aucun serveur à gérer : collecte, transformation et export de données météo pour six villes d'Afrique de l'Ouest (Dakar, Thiès, Saint‑Louis, Bamako, Abidjan, Ouagadougou). L'intérêt est de manipuler de vrais services managés AWS et un déclenchement événementiel plutôt qu'une simple tâche planifiée.

Lambda‑Collecte interroge l'API OpenWeatherMap pour chaque ville et dépose la réponse brute en JSON dans un bucket S3, sous un chemin daté (raw/Ville/AAAA/MM/JJ/HH‑MM‑SS.json). Le dépôt d'un nouveau fichier déclenche automatiquement Lambda‑Traitement via un événement S3 : la fonction extrait température, humidité, pression et vent, calcule les min/max/moyennes du jour en les combinant aux mesures déjà enregistrées dans DynamoDB (clé composite ville#date), puis déplace le fichier de raw/ vers processed/. Enfin, Lambda‑Export génère chaque semaine un rapport CSV consolidé sur 7 jours et le publie dans S3.

AWS Lambda Amazon S3 Amazon DynamoDB Python (boto3) API OpenWeatherMap ETL événementiel

Application de prétraitement de données (FastAPI + Streamlit)

Nettoyage guidé de datasets CSV/Excel, sans boîte noire

Data Engineering

L'intérêt de ce projet est de transformer une tâche que tout data scientist répète sans cesse — le nettoyage de données — en une application guidée et transparente. L'utilisateur charge un fichier CSV ou Excel et progresse à travers un pipeline en 6 étapes ; à chaque étape, l'application analyse statistiquement les données et recommande une méthode de traitement adaptée, sans jamais l'imposer : l'utilisateur garde la main pour valider ou changer chaque recommandation.

Architecture en deux services découplés : une interface Streamlit qui ne contient aucune logique de traitement (elle affiche et appelle l'API), et un backend FastAPI qui porte toute la logique métier. Le fichier n'est envoyé qu'une seule fois (POST /upload) ; l'API renvoie un identifiant de dataset, et toutes les étapes suivantes le référencent plutôt que de renvoyer le fichier entier à chaque appel — le DataFrame vit en mémoire côté serveur et se transforme progressivement.

Voir le détail des 6 étapes du pipeline

1. Analyse initiale — détection automatique des types de colonnes, taux de valeurs manquantes, asymétrie (skewness), corrélations, et détection de séries temporelles.

2. Valeurs manquantes — un test statistique (Student pour le numérique, Chi² pour le catégoriel) détermine si l'absence de valeur est aléatoire (MCAR) ou liée à d'autres colonnes (MAR/MNAR), et recommande en conséquence des méthodes simples (moyenne, médiane, mode, interpolation) ou avancées (KNNImputer, IterativeImputer, imputation par groupe temporel). Le motif des valeurs manquantes est visualisé via une matrice missingno.

3. Valeurs aberrantes — la méthode est choisie selon l'asymétrie de la distribution : Z‑score (symétrique), IQR (asymétrie modérée), ou Winsorisation (forte asymétrie), avec comparaison visuelle avant/après.

4. Feature scaling — RobustScaler en priorité si des outliers sont détectés, sinon StandardScaler ou MinMaxScaler selon la distribution.

5. Encodage — Label Encoding, One‑Hot Encoding, ou encodage ordinal avec ordre personnalisable directement depuis l'interface, selon la cardinalité de chaque variable.

6. Visualisation & export — résumé avant/après, journal complet des traitements appliqués, export CSV du dataset nettoyé, et génération d'un script Python autonome reproduisant fidèlement tout le pipeline appliqué — utile pour vérifier qu'il n'y a aucune boîte noire, ou pour réutiliser le traitement ailleurs.

L'ensemble est couvert par 58 tests pytest (dont un test d'intégration end‑to‑end du pipeline complet), conteneurisé avec Docker/docker‑compose, et intégré à une CI GitHub Actions qui relance la suite de tests à chaque push.

FastAPI Streamlit Pandas / NumPy Scikit‑learn SciPy Plotly / Matplotlib Pytest (58 tests) Docker CI/CD GitHub Actions

FraudGuard — Détection de fraude bancaire par carte de crédit

284 807 transactions, 0,17% de fraudes : modélisation, API et dashboard

Machine Learning supervisé

Ce projet traite un problème classique mais exigeant : détecter une fraude extrêmement rare (492 fraudes sur 284 807 transactions du jeu de données Credit Card Fraud Detection (ULB)) sans se laisser piéger par le déséquilibre de classes. Son intérêt est de montrer une démarche de modélisation complète et honnête : exploration en notebook, comparaison rigoureuse de plusieurs modèles, choix de métriques adaptées, puis mise en production via une API et un dashboard.

⚠️ L'accuracy n'est jamais utilisée comme métrique de référence : avec 99,83% de transactions normales, un modèle qui prédirait toujours « normal » atteindrait déjà 99,83% d'accuracy sans détecter la moindre fraude. Toutes les décisions s'appuient sur precision, recall, F1 et PR‑AUC.

ModèlePrecisionRecallF1PR‑AUC
Logistic Regression0,0610,9180,1140,716
Random Forest0,8420,8160,8290,829
XGBoost (retenu)0,8820,8370,8590,879
Voir la démarche complète et les résultats détaillés

XGBoost (avec scale_pos_weight pour compenser le déséquilibre) est retenu face à la régression logistique et à la random forest. Un seuil de décision optimisé à 0,9238 (au lieu de 0,5 par défaut) améliore encore le compromis : precision 0,882 → 0,942, F1 0,859 → 0,880. Une validation croisée à 5 plis confirme la stabilité du résultat (PR‑AUC moyen 0,855 ± 0,018).

SMOTE testé et écarté : le sur‑échantillonnage synthétique de la classe minoritaire donne un PR‑AUC légèrement inférieur (0,862) à la simple pondération de classe — sur ce dataset, scale_pos_weight est suffisant et plus simple à maintenir.

Le modèle entraîné dans le notebook est sauvegardé (.joblib) puis chargé au démarrage par une API FastAPI qui expose le scoring en temps réel, sans aucune dépendance à Jupyter en production. Un dashboard Streamlit (« FraudGuard ») consomme cette API pour proposer une interface de test interactive. L'ensemble est couvert par 16 tests pytest (chargement du modèle, cohérence des prédictions, robustesse à l'ordre des colonnes, validation des entrées, endpoint batch) et intégré à une CI GitHub Actions.

Limites assumées : modèle entraîné sur des données de 2013 (un recalibrage serait nécessaire avant tout usage réel), stockage local des artefacts sans registre de modèles versionné, pas d'authentification sur l'API — autant de points identifiés et documentés plutôt que passés sous silence.

Python XGBoost Scikit‑learn FastAPI Streamlit Pytest (16 tests) Docker CI/CD GitHub Actions
Code source (GitHub) Démo FraudGuard (Streamlit)

Churn Radar — Prédiction du churn client (Telco)

Démarche ML de bout en bout, en 6 missions cadrées

Machine Learning supervisé

Ce projet répond à un vrai problème métier : un opérateur télécom veut anticiper les clients sur le point de résilier pour leur adresser en priorité une offre de rétention, sachant qu'un faux négatif coûte bien plus cher qu'un faux positif. Son intérêt est de suivre une méthodologie complète et vérifiable, en 6 étapes cadrées à l'avance (cadrage, exploration, pipeline sans fuite, benchmark de modèles, optimisation/interprétabilité, déploiement), sur ~7 000 clients avec 27% de taux de churn.

ÉtapeRésultat clé
Cadrage (M0)Métrique F1 retenue, seuil de réussite F1 ≥ 0,60 fixé a priori
Exploration (M1)Aucune fuite de données détectée ; 3 hypothèses métier confirmées
Pipeline (M2)ColumnTransformer fit uniquement sur train ; feature engineering testé puis écarté (pas de gain)
Benchmark (M3)LightGBM, XGBoost et Logistic Regression quasi ex æquo (F1 ≈ 0,63)
Optimisation (M4)Tuning Optuna (60 essais), calibration isotonique, interprétabilité SHAP
Déploiement (M5)API FastAPI + dashboard Streamlit, Docker, 5 tests pytest
Voir le choix du modèle final et l'interprétabilité

Le test de Wilcoxon entre LightGBM et la régression logistique donne p = 0,4375 (non significatif) : l'écart de performance ne justifiant pas de sacrifier l'interprétabilité, c'est la régression logistique calibrée qui est retenue comme modèle final, conformément à l'exigence d'explicabilité fixée dès le cadrage (M0).

Le tuning Optuna (60 essais, 6 hyperparamètres) porte le F1 à 0,6335 — la pondération de classe (class_weight) expliquant à elle seule 96,9% du gain. La calibration isotonique réduit le Brier score de 0,169 à 0,140. L'analyse SHAP montre que MonthlyCharges et tenure dominent : charges élevées et faible ancienneté poussent vers le churn, tandis qu'un contrat de 2 ans protège fortement. Le seuil de décision est optimisé à 0,13 (F2‑score), très inférieur à 0,5, pour maximiser le rappel conformément aux coûts d'erreur définis en amont.

Le dashboard Streamlit propose 5 pages (vue d'ensemble, prédiction en direct, exploration des données, performance du modèle, à propos), et un plan de monitoring complet est documenté (MODEL_CARD.md, MONITORING.md) : suivi du data drift (PSI / Kolmogorov‑Smirnov), du concept drift et de la performance dans le temps, avec l'outil open‑source Evidently AI recommandé.

Python Scikit‑learn LightGBM / XGBoost Optuna SHAP FastAPI Streamlit Docker Pytest

StageFlow — API sécurisée de gestion des stages

API métier multi‑rôles, sans interface : FastAPI + PostgreSQL

Backend / API

Ce projet n'a volontairement pas d'interface graphique : c'est une API interne pure, ce qui en fait un bon test de la qualité d'une architecture backend « nue », jugée sur sa documentation OpenAPI, ses tests et sa rigueur d'implémentation plutôt que sur son rendu visuel. Elle permet à un établissement de suivre les offres de stage, les candidatures, les validations pédagogiques et les avis des encadrants.

Quatre rôles aux permissions distinctes : l'étudiant consulte les offres publiées, candidate, suit et retire ses candidatures ; l'entreprise crée des offres en brouillon, les soumet, et ne voit que les candidatures de ses propres offres ; le responsable pédagogique publie ou refuse une offre, accepte ou refuse une candidature, et consulte les statistiques globales ; l'admin gère les comptes.

Le point d'architecture le plus intéressant : la table Entreprise est séparée du rôle applicatif. Le rôle entreprise gère les permissions, mais une entreprise est une entité métier à part entière (nom, description), liée en 1‑à‑1 au compte utilisateur. Cette séparation est nécessaire pour respecter deux règles strictes : une offre doit être rattachée à une entreprise précise, et une entreprise ne doit voir que les candidatures de ses offres — une isolation qui repose sur la comparaison entre entreprises, pas sur l'identifiant utilisateur.

Authentification par JWT (access + refresh tokens), base PostgreSQL via SQLAlchemy asynchrone, migrations gérées par Alembic (appliquées automatiquement au démarrage du conteneur Docker), et architecture en couches stricte : aucune route n'appelle SQLAlchemy directement, tout passe par une couche repositories/. Les tests utilisent une base SQLite en mémoire, isolée de la base de développement, et la qualité du code est vérifiée par ruff et mypy.

FastAPI PostgreSQL SQLAlchemy (async) Alembic JWT Docker Compose Pytest Ruff / Mypy

Clustering des foyers londoniens — London Smart Meters

Deux approches de clustering non supervisé, comparées et validées

Machine Learning non supervisé

Ce projet exploite les données de compteurs intelligents de Londres (London Smart Meters, Kaggle) — des milliers de foyers mesurés toutes les demi‑heures — pour répondre à une question business : peut‑on regrouper les foyers en profils de consommation types, utiles à un fournisseur d'électricité pour adapter ses offres tarifaires ? Son intérêt est de comparer deux approches méthodologiquement différentes du même problème plutôt que de se contenter d'un seul algorithme.

Approche B (features) — chaque foyer est résumé par ses 48 valeurs moyennes demi‑horaires normalisées (forme de la courbe indépendamment du volume), puis regroupé par K‑means, CAH, GMM et DBSCAN. Approche A (DTW) — au contraire, elle travaille directement sur la forme temporelle brute des courbes de charge, à l'aide de la distance Dynamic Time Warping, avec K‑means DTW, CAH et K‑Shape.

Voir la démarche de validation et les conclusions métier

La robustesse de chaque approche est vérifiée par l'Adjusted Rand Index entre méthodes (convergence entre K‑means, CAH, GMM/K‑Shape) et par une analyse de stabilité temporelle (les clusters obtenus sur une période restent‑ils cohérents sur une autre ?). Le tableau de bord Streamlit multi‑pages reproduit l'intégralité de la démarche : EDA (volumétrie, distributions, courbes de charge moyennes, effets saison / calendrier / météo), Approche B, Approche A, et une synthèse comparative qui croise les deux approches avec le profil socio‑économique ACORN et le type de tarif souscrit.

La synthèse conclut sur l'implication métier : les clusters qui se retrouvent de façon cohérente dans les deux approches sont ceux sur lesquels un fournisseur d'électricité peut construire des offres différenciées avec le plus de confiance, tandis que les foyers aux profils instables entre approches appellent à la prudence avant toute segmentation commerciale.
