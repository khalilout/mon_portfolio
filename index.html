Plateforme Articles & Amis

Full-stack

API Laravel + front React — réseau social minimaliste

Ce projet met en avant ma capacité à livrer une application de bout en bout : une API REST sécurisée d'un côté, une interface React moderne de l'autre. N.02

Pipeline météo serverless

Cloud / ETL

AWS Lambda, S3 & DynamoDB — 100% serverless

Ce projet illustre une chaîne ETL serverless complète sur AWS, sans aucun serveur à gérer : collecte, transformation et export de données météo pour six villes d'Afrique de l'Ouest (Dakar, Thiès, Saint-Louis, Bamako, Abidjan, Ouagadougou). L'intérêt est de manipuler de vrais services managés AWS et un déclenchement événementiel plutôt qu'une simple tâche planifiée.

Lambda-Collecte interroge l'API OpenWeatherMap pour chaque ville et dépose la réponse brute en JSON dans un bucket S3, sous un chemin daté (raw/Ville/AAAA/MM/JJ/HH-MM-SS.json). Le dépôt d'un nouveau fichier déclenche automatiquement Lambda-Traitement via un événement S3 : la fonction extrait température, humidité, pression et vent, calcule les min/max/moyennes du jour en les combinant aux mesures déjà enregistrées dans DynamoDB (clé composite ville#date), puis déplace le fichier vers processed/. Enfin, Lambda-Export génère chaque semaine un rapport CSV consolidé.

N.03

Application de prétraitement de données

Data engineering

FastAPI + Streamlit — nettoyage guidé, sans boîte noire

L'intérêt de ce projet est de transformer une tâche que tout data scientist répète sans cesse — le nettoyage de données — en une application guidée et transparente. L'utilisateur charge un fichier CSV ou Excel et progresse à travers un pipeline en 6 étapes ; à chaque étape, l'application analyse statistiquement les données et recommande une méthode adaptée, sans jamais l'imposer.

Architecture en deux services découplés : une interface Streamlit sans aucune logique de traitement, et un backend FastAPI qui porte toute la logique métier. Le fichier n'est envoyé qu'une seule fois ; toutes les étapes suivantes référencent un identifiant de dataset plutôt que de renvoyer le fichier entier à chaque appel.

Voir le détail des 6 étapes du pipeline

1. Analyse initiale — types de colonnes, valeurs manquantes, asymétrie, corrélations, séries temporelles.

2. Valeurs manquantes — un test statistique (Student / Chi²) détermine si l'absence est aléatoire (MCAR) ou liée à d'autres colonnes (MAR/MNAR), et recommande imputation simple ou avancée (KNNImputer, IterativeImputer).

3. Valeurs aberrantes — Z-score, IQR ou Winsorisation selon l'asymétrie de la distribution.

4. Feature scaling — RobustScaler si outliers détectés, sinon StandardScaler ou MinMaxScaler.

5. Encodage — Label / One-Hot / ordinal personnalisable selon la cardinalité.

6. Visualisation & export — journal des traitements, export CSV, et génération d'un script Python autonome reproduisant le pipeline — pour vérifier qu'il n'y a aucune boîte noire.

L'ensemble est couvert par 58 tests pytest, conteneurisé (Docker/docker-compose), et intégré à une CI GitHub Actions.

N.04

FraudGuard — détection de fraude bancaire

Machine learning supervisé

284 807 transactions, 0,17% de fraudes : modélisation, API et dashboard

Ce projet traite un problème classique mais exigeant : détecter une fraude extrêmement rare (492 fraudes sur 284 807 transactions du jeu de données Credit Card Fraud Detection, ULB) sans se laisser piéger par le déséquilibre de classes.

⚠️ L'accuracy n'est jamais utilisée comme métrique de référence : avec 99,83% de transactions normales, un modèle qui prédirait toujours « normal » atteindrait déjà cette accuracy sans détecter la moindre fraude. Toutes les décisions s'appuient sur precision, recall, F1 et PR-AUC.

ModèlePrecisionRecallF1PR-AUC
Logistic Regression0,0610,9180,1140,716
Random Forest0,8420,8160,8290,829
XGBoost (retenu)0,8820,8370,8590,879
Voir la démarche complète et les résultats détaillés

XGBoost (avec scale_pos_weight) est retenu face à la régression logistique et la random forest. Un seuil optimisé à 0,9238 améliore encore le compromis : precision 0,882 → 0,942, F1 0,859 → 0,880. Une validation croisée à 5 plis confirme la stabilité (PR-AUC moyen 0,855 ± 0,018).

SMOTE testé et écarté : PR-AUC légèrement inférieur (0,862) à la simple pondération de classe. Le modèle est chargé par une API FastAPI et consommé par un dashboard Streamlit (FraudGuard). 16 tests pytest et CI GitHub Actions complètent l'ensemble.

Limites assumées : données de 2013 (recalibrage nécessaire avant usage réel), pas de registre de modèles versionné, pas d'authentification sur l'API.

N.06

Churn Radar — prédiction du churn client

Machine learning supervisé

Telco — démarche ML de bout en bout, en 6 missions cadrées

Un opérateur télécom veut anticiper les clients sur le point de résilier, sachant qu'un faux négatif coûte bien plus cher qu'un faux positif. Le projet suit une méthodologie cadrée en 6 étapes sur ~7 000 clients (27% de churn) : cadrage, exploration, pipeline sans fuite, benchmark de modèles, optimisation/interprétabilité, déploiement.

ÉtapeRésultat clé

ExplorationAucune fuite détectée · 3 hypothèses métier confirmées
BenchmarkLightGBM / XGBoost / LogReg quasi ex æquo (F1 ≈ 0,63)
OptimisationOptuna (60 essais) · calibration · SHAP
DéploiementAPI FastAPI + dashboard Streamlit, Docker, pytest
Voir le choix du modèle final et l'interprétabilité

Le test de Wilcoxon entre LightGBM et la régression logistique donne p = 0,4375 (non significatif) : c'est donc la régression logistique calibrée qui est retenue, conformément à l'exigence d'explicabilité fixée dès le cadrage.

Le tuning Optuna porte le F1 à 0,6335 — la pondération de classe expliquant 96,9% du gain. L'analyse SHAP montre que MonthlyCharges et tenure dominent. Le seuil de décision est optimisé à 0,13 (F2-score) pour maximiser le rappel. Un plan de monitoring complet est documenté (PSI, Kolmogorov-Smirnov, Evidently AI).

N.07

StageFlow — API de gestion des stages

Backend / API

Sans interface graphique : FastAPI + PostgreSQL, multi-rôles

Ce projet n'a volontairement pas d'interface graphique : une API interne pure, jugée sur sa documentation OpenAPI, ses tests et sa rigueur d'implémentation. Elle permet de suivre offres de stage, candidatures, validations pédagogiques et avis des encadrants, à travers quatre rôles aux permissions distinctes (étudiant, entreprise, responsable pédagogique, admin).

Point d'architecture notable : la table Entreprise est séparée du rôle applicatif — une entreprise est une entité métier à part entière, liée en 1-à-1 au compte utilisateur, ce qui permet une isolation stricte : une entreprise ne voit que les candidatures de ses offres. Authentification JWT (access + refresh), PostgreSQL via SQLAlchemy asynchrone, migrations Alembic automatiques au démarrage, architecture en couches stricte (routes → repositories), tests sur SQLite en mémoire, qualité vérifiée par ruff et mypy.

N.08

Clustering des foyers londoniens

Machine learning non supervisé

London Smart Meters — deux approches comparées et validées

Ce projet exploite les données de compteurs intelligents de Londres (London Smart Meters, Kaggle) pour répondre à une question business : peut-on regrouper les foyers en profils de consommation types ? Approche B (features) résume chaque foyer par ses 48 valeurs moyennes demi-horaires normalisées (K-means, CAH, GMM, DBSCAN). Approche A (DTW) travaille sur la forme temporelle brute des courbes de charge (K-means DTW, CAH, K-Shape).

Voir la démarche de validation et les conclusions métier

La robustesse est vérifiée par l'Adjusted Rand Index entre méthodes et par une analyse de stabilité temporelle. Le dashboard Streamlit multi-pages reproduit toute la démarche (EDA, Approche A, Approche B, synthèse comparative croisant les deux approches avec le profil socio-économique ACORN et le type de tarif).

Conclusion métier : les clusters cohérents entre les deux approches sont ceux sur lesquels un fournisseur d'électricité peut construire des offres différenciées avec confiance ; les profils instables appellent à la prudence.
